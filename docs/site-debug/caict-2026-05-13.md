## ⚠️ 第 0 步（最重要）：现场数据库初始化

### 背景一句话

5/11 已合到 main 的两件治本动作：
- **alembic** 接管 schema 迁移——以后 model 改字段必须配迁移文件，不再 schema drift。
- **bootstrap 框架** 接管默认数据——商用部署开箱即用，但只发**通用**预设，不绑场地。

现场要做的就是**把这两件事跑一遍**。

### 现场操作（到达后立刻做，先于一切其他事）

```bash
# 1. 拉取最新代码（含 alembic 迁移文件 + bootstrap）
cd ~/MIMO-First   # 或部署路径
git pull

# 2. 进入后端目录，启用 venv
cd api-service
source .venv/bin/activate

# 3. 看一眼 DB 当前在哪个版本
alembic current
#   情况 A: 输出 "(empty)"      → 现场 PG 从未跑过 alembic
#   情况 B: 输出某个 revision id → 已经跑过, 但可能旧

# 4. 应用所有未执行的 schema 迁移
alembic upgrade head
#   预期: 输出 "Running upgrade ... -> e863f092696b"

# 5. 跑 bootstrap, 落入 4 个默认暗室预设 + 仪器目录 + 序列 + 报告模板 + 测试用例
python -m scripts.bootstrap
#   预期(首次):
#     chamber_presets      ran  (+4  / =0)
#     probes               ran  (+32 / =0)
#     instruments          ran  (+38 / =0)
#     sequences            ran  (+14 / =0)
#     report_templates     ran  (+6  / =0)
#     test_case_templates  ran  (+25 / =0)
#   再跑一次: 全部 "skipped (up-to-date)"

# 6. 验证
alembic current
#   预期输出: e863f092696b (head)

curl -w "\nHTTP %{http_code}\n" http://localhost:8000/api/v1/chambers
#   预期: HTTP 200，items 里恰好 4 个 "默认 - " 开头的 chamber
```

### 情况 A 特殊处理：现场 PG 从未跑过 alembic

如果 `alembic current` 输出 `(empty)`，需要先把 DB 标为 baseline 版本：

```bash
alembic stamp 40fd1c51ff40   # 把现状标为 baseline (不跑任何 SQL)
alembic upgrade head         # 升级到最新
python -m scripts.bootstrap  # 落默认数据
```

### 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `alembic` 命令不存在 | 没启用 venv | `source .venv/bin/activate` 后重试 |
| `psycopg2.OperationalError: could not connect` | DATABASE_URL 配错 | 检查 `.env` 的 `DATABASE_URL=postgresql://...`，确认 PG 在跑 |
| `permission denied for table ...` | PG 用户没有 DDL 权限 | 用 superuser 重跑，或临时 `GRANT ALL ON ALL TABLES IN SCHEMA public TO <user>` |
| `relation alembic_version already exists` | 已经 stamp 过了 | 直接 `alembic upgrade head` |
| `could not find table for foreign key` | 迁移逻辑 bug | 截图发后端，**不要硬改迁移文件** |
| bootstrap 某个 seeder failed | 数据约束 / 列不一致 | 先确认 `alembic current` 显示 `e863f092696b`；若是，截图 traceback |
| 看不到 4 个 "默认 -" chamber | bootstrap 没跑或失败 | `python -m scripts.bootstrap --force` 重跑；看输出 |
| **找不到原来的 "CAICT-Lab-1" / "CATR-..." 暗室** | **正常现象**——这些场地命名的预设已经从商用代码移除了（见下节） | 按 09:45 那一步**手工建一个**：选 Type C/D 预设 → 复制 → 改名 |

## 第 0.5 步：理解新的「暗室预设」机制（一定要看）

5/11 之前 DB 里可能见过 `CAICT-Lab-1`、`CATR-...` 这类**场地命名**的暗室。
**它们已经从系统预设里移除了**——商用代码不应硬编码客户场地。重构后：

### 4 个**通用**系统预设（bootstrap 自动落入）

| GUI 显示名 | chamber_type | 物理形态 | 典型用途 |
|---|---|---|---|
| 默认 - 小型无源暗室 | `type_a` | 小型，无源 | 手机/模块 TRP / TIS |
| 默认 - 小型 MIMO 暗室 | `type_b` | 小型，多探头 | 手机 MIMO OTA |
| 默认 - 大型单向暗室 | `type_c` | 大型，下行测向 | **车载 MIMO OTA**（多数现场用这个） |
| 默认 - 大型双向暗室 | `type_d` | 大型，双向通信 | 车载全功能（含上下行联测） |

这 4 个预设标了 `is_system_preset=True`，**只读**——GUI 上 PUT/DELETE 会返回 409。

### 场地暗室怎么落地？

工作流：**选预设 → 复制 → 改名 → 改参数**

```
GUI:「探头与暗室配置」页面
  ├─ 选「默认 - 大型单向暗室」(假设 CAICT 现场是 Type C)
  ├─ 点右上角「复制配置」按钮
  └─ 自动得到「默认 - 大型单向暗室 (副本)」
       ├─ 重命名 → "CAICT-Lab-1 现场"
       ├─ 改参数 (尺寸、探头数、cable_sgh_to_sa_loss_db ...)
       ├─ 标记 is_active=true
       └─ 副本上 is_system_preset=False，能改能删
```

### 旧的 `seed_caict_lab_profile.py` 去哪了？

迁到了 `api-service/scripts/dev-fixtures/`，**不在 bootstrap 链里**。
仅本机开发图省事时可以手动跑：

```bash
cd api-service
.venv/bin/python scripts/dev-fixtures/seed_caict_lab_profile.py
# 现场不需要跑——用"复制+改名"工作流更干净，能落 git 也能落 DB
```

## 三、5-Phase 验收 Gate

| Phase | 名称 | 关键产出 | 验收（PASS） |
|---|---|---|---|
| 1. PRECHECK | 系统预检 | `precheck.measurements.overall_pass=true` | critical instruments online + QZ ripple ≤ 阈值 + UE 4×4 capability |
| 2. REFERENCE | 参考天线基线 | SGH 在 QZ 中心的接收功率 | 与 link budget 计算值 ±1.5 dB 内 |
| 3. MEASURE | 静态 MIMO 吞吐量 | DL throughput 曲线（vs SS-RSRP） | 至少 1 个 RSRP 点上 throughput ≥ 90% peak |
| 4. ANALYSIS | CTIA pass/fail | margin (dB)、统计样本数 | margin > 0 dB |
| 5. REPORT | 报告归档 | PDF + JSON + raw CSV | 文件落到 `report_storage/`，可下载 |

> 任何 phase 失败：保留 `test_executions.execution_logs` + `phase_results` + `hardware_status` 三个 JSON blob 截图，**不要清表**——回去复盘要用。

| 风险 | 触发条件 | 降级方案 |
|---|---|---|
| **DB 没初始化** | `/chambers` 返回 500 / 拓扑编辑器加载失败 / 暗室列表为空 | **立即跑第 0 步**；不要继续往后 |

| 试图改系统预设报 409 | 「is system preset and cannot be edited」 | 这是设计——点 GUI 上的「**复制配置**」按钮，在副本上改 |
| **UXM SCPI Critical UNSUPPORTED** | probe 脚本报告 critical 命令 -113 / -114(Undefined header) | 1. 查 `probe_uxm_scpi.py` 输出里 UNSUPPORTED 段的具体命令; 2. 翻 UXM 现场 firmware 的 SCPI Reference 找对应命令的现行名; 3. 在 `app/hal/uxm_base_station.py::UxmScpiCommands` 改对应常量(典型差异:V10/V11 `:UE:CAPability` ↔ V12+ `:UEINFO:CAPability`); 4. 重启 API 服务,重跑 probe |
| **UXM SCPI non-critical UNSUPPORTED** | probe 报告 CSI/EVM/UE_RSRP 等查询缺失 | 跳过 — driver 的 `hasattr(base_station, "X")` 模式会自动降级,phase 里只标 warning 不 fail。回北京再补 alias |
| UXM SCPI 状态错误 (-200 系列) | probe 报告 SUPPORTED_BUT_STATE | 正常 — 这只是"命令存在,但当前 UXM 状态不让查"(如 cell 没起来时查 throughput)。Phase 跑起来后自动 OK |
| F64 user alignment 没 license | `SYST:CALIB:USER:GET?` 返回 error | precheck 只 warning 不 fail；走 factory cal，记录到 phase 注释 |
| SGH cable loss 未测 | `cable_sgh_to_sa_loss_db` NULL | 路损校准 fallback 到 legacy VNA 路径；标注此次校准 "unverified" |
| DUT 不 attach | RRC 长时间 IDLE | 检查 IMSI / SIM / 频段；最差切到 manual SIM 场景，跳 attach phase |
| QZ ripple 超阈 | `quiet_zone_ripple_db > 0.7` | 不要硬跑；先 import vendor probe pattern (`/api/v1/calibration/probe/pattern/import`) |
