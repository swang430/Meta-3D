## 编号与状态规则

- `RT24-001`～`RT24-053` 是本次计划的独立稳定编号；旧 `T/C/R/G/B/V`、`PC`、`P0/P1/P2`、`NEW` 编号均保留。当前优先序可以调整，计划ID不随排序变化。
- 本队列用于排开发与验证依赖，不自行授权开发范围或现场执行。原功能/缺陷状态仍以 `docs/roadmap-first-call.md` 为准；云端日期和实进度以甘特表为准。
- 优先级 `P0/P1/P2` 仅表示本24周计划的调度紧迫度，不是仓库 Code Review 严重度。排序首先考虑逾期前置、安全/方法/资格门槛，其次考虑当前及下一窗口，再考虑后续验证。
- “现场/外部阻塞”行是甘特未单列但会阻塞目标任务的前置条件；建议窗口仅用于排期讨论，不是原甘特承诺日期。PC-09仍是HOLD，不因进入索引而解锁。
- 完成判据：代码合并、Mock、诊断运行和报告生成不能代替真实设备、CTIA或38.901正式验证；所有B项须由原始证据及负责人签认解除。

## 检索与更新方法

1. 在云端“RT24优先队列”按计划ID查任务；在原“甘特计划”按旧ID查日期、依赖、验收依据、真实进度；在仓库按原todo编号查实施与现场关闭条件。
2. 反向查找时，在本表“甘特ID/受影响项”或“原todo编号”筛选，即得计划ID。原甘特行右侧也记录对应计划ID，便于从任务直接跳回本队列。
3. 每次调整优先序，记录日期、原因、对后继窗口的影响；不重用或重排计划ID。只有经负责人确认的窗口变更才修改原甘特日期。
4. 现场阻塞一旦取得证据，先更新原todo/B项及云端“评审验证输入”，再更新本表状态，最后按原甘特验收依据更新实进度；缺任何一层均不能标“完成”。
