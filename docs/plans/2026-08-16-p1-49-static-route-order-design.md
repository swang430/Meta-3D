# P1-49 静态路由遮挡修复设计

## 可观察故障

FastAPI 按声明顺序匹配路由。当前两个静态 GET 端点声明在同级 UUID 参数路由之后：

- `/api/v1/calibration/channel/temporal/latest`
- `/api/v1/topologies/default`

真实请求会先命中 `/{calibration_id}` 或 `/{topology_id}`，把 `latest` / `default`
当成 UUID 解析并返回 422，静态端点不可达。

## 选择方案

采用最小的声明顺序修复：把两个静态 GET 路由分别移动到同级 UUID 参数 GET 路由之前。
不修改 URL、schema、服务查询、数据库模型、错误语义或前端调用。

未采用的方案：

- 改造参数路由路径：会破坏既有 API 契约。
- 引入统一路由注册封装：对两个明确的声明顺序故障而言机制过重。

## 行为与错误处理

- 静态路由优先命中原有 handler。
- 找不到最新时域校准或默认拓扑时，继续返回各 handler 既有的 404。
- 合法 UUID 仍命中原详情 handler，响应与错误语义不变。
- 不增加 fallback；静态请求不得再落入 UUID 校验错误。

## 测试与守门

1. 先补真实 HTTP 回归，证明两个静态请求在旧顺序下返回 UUID 解析 422。
2. 调整声明顺序后，两条 HTTP 回归应命中静态 handler；测试数据不存在时允许原生 404，
   但不得出现 `uuid_parsing`。
3. 保留合法 UUID 详情路由回归，防止静态路由移动误伤参数路径。
4. 从 G19 删除两个存量精确例外，使全仓静态路由遮挡集合恢复为空。
5. 运行相关 HTTP 回归、完整 rule gates、compileall 与 diff-check。
