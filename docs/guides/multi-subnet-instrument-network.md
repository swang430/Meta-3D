# 多子网仪表网络配置指南

> 控制电脑如何在**不修改仪表默认 IP** 的前提下，灵活控制分布在不同子网上的仪表。
>
> Roadmap: **P1-11**。本指南是网络/操作系统层的 runbook；MIMO-First 软件侧的
> 可达性诊断增强见末尾「软件侧支持」。

---

## 1. 问题

仪表出厂/现场默认 IP 落在不同 `/24` 子网，一般不去改它们。典型 CAICT 现场
（2026-05-13 实测）：

| 仪表 | 子网 | 示例 IP |
|------|------|---------|
| PROPSIM F64（信道仿真器） | `192.168.0.0/24` | `192.168.0.132` |
| UXM E7515B（基站仿真器） | `192.168.1.0/24` | `192.168.1.112` |
| N9042B（信号分析仪） | `192.168.1.0/24` | `192.168.1.55` |

控制电脑（调试 Mac）**只有一张活动网卡**。当它的静态 IP 配在 `192.168.0.x`
时只能跟 F64 通信，配在 `192.168.1.x` 时只能跟 UXM/SA 通信——这就是现场反复出现
的「F64 ✓ + UXM ✗」⇄「UXM ✓ + F64 ✗」交替，操作员被迫**手工来回改静态 IP**。
CAICT 两天现场有相当一部分时间耗在这种子网切换的来回上。

**核心原则**：
1. **不改仪表 IP** —— 仪表保持默认地址。
2. **这是网络/OS 层问题，不是 MIMO-First 软件问题** —— 单网卡 PC 能否同时够到
   多子网，取决于 OS 网络/路由配置。软件只能*诊断*哪个子网可达，改不了路由。
3. 让 PC「在所有相关子网都有直连接口或可路由路径」，仪表的连接字符串
   （`TCPIP0::192.168.0.132::inst0::INSTR` 等）就无需任何改动。

---

## 2. 方案 A —— 单网卡挂多个 IP 别名（便携首选，零硬件）✅

**适用前提**：所有仪表挂在**同一台物理交换机、无 VLAN 隔离**（同一 L2 广播域，
只是 IP 在不同子网）。CAICT 现场即此情形。

**原理**：给控制 PC 的**那一张物理网卡同时配多个子网的 IP**。PC 于是在每个子网
都有一个「直连」接口，发往任一子网的报文都能直接走二层送达，**无需路由器**，也
不用再手工切换。

```
en0 (单张网卡):
   192.168.0.10/24   ← 与 F64 同段，直接可达
   192.168.1.10/24   ← 与 UXM / SA 同段，直接可达
```

### macOS（控制 Mac）

临时（重启后失效，现场快速验证用）：
```bash
# 第一个子网（主 IP，通常已在系统设置里配好）
sudo ifconfig en0 192.168.0.10 netmask 255.255.255.0
# 追加第二个子网的别名（关键：alias，不是覆盖）
sudo ifconfig en0 alias 192.168.1.10 netmask 255.255.255.0
```
> 选与仪表不冲突的主机位（如 `.10`），避开仪表已用的 `.132` / `.112` / `.55`。

持久（推荐，重启保留）：在「系统设置 → 网络」里为同一物理网口**新增一个
Service / 配置**，分别静态配 `192.168.0.10/24` 和 `192.168.1.10/24`；或用
`networksetup`：
```bash
# 查网口对应的硬件 service 名
networksetup -listallnetworkservices
# 主子网
sudo networksetup -setmanual "Ethernet" 192.168.0.10 255.255.255.0
# 第二子网：复制一个网络位置/Service 后设第二个静态 IP
# (GUI 操作最稳；CLI 别名持久化在 macOS 上不如 GUI Service 可靠)
```

### Linux（若控制机是 Linux）
```bash
sudo ip addr add 192.168.0.10/24 dev eth0
sudo ip addr add 192.168.1.10/24 dev eth0   # 同一网卡，第二个子网
ip addr show eth0                            # 应看到两个 inet
```
持久：写进 netplan / NetworkManager（`nmcli con mod <con> +ipv4.addresses 192.168.1.10/24`）。

### 验证
```bash
ping 192.168.0.132     # F64
ping 192.168.1.112     # UXM
# SCPI 端口连通（比 ping 更准，有些仪表禁 ICMP）：
nc -vz 192.168.0.132 5025
nc -vz 192.168.1.112 5025
```
两个子网都通 = 成功。此后操作员**不用再切静态 IP**——两个都挂着即可。

### 注意事项
- **主机位不要和任何仪表/其它设备撞**。
- **网关**：多子网场景通常不需要默认网关（都是直连 link-local 通信）。若确实要
  访问外网，只在一个子网配默认网关，其余子网纯直连。
- 别名子网之间不重叠（`/24` 互不包含），否则路由表会歧义。
- 此方案**只在平坑 L2 成立**。若仪表被 VLAN 隔离 / 分接不同交换机，见方案 B/C。

## 3. 方案 B —— 三层交换机 / 小路由器做子网间路由（固定实验室首选，最稳）

**适用**：固定实验室、子网/仪表多、要重启不丢配置、或仪表被 VLAN/物理分隔。

**原理**：PC 只配**一个 IP + 默认网关指向路由器**；路由器（或三层交换机的 SVI）
在每个仪表子网各有一个接口，负责子网间转发。

```
PC (单 IP, 192.168.10.10/24, gw=192.168.10.1)
        │
   [三层交换机 / 路由器]
   SVI 192.168.0.1/24 ── F64 子网
   SVI 192.168.1.1/24 ── UXM / SA 子网
```

**关键约束**：仪表保持默认 IP，但**仪表的默认网关要指向路由器对应 SVI**
（如 F64 网关设 `192.168.0.1`），否则跨子网的回程报文无法返回 PC。若仪表无法
配网关，则退回方案 A（PC 直接在仪表子网有接口，纯二层，不依赖仪表网关）。

- 优点：扩展到 N 个子网都行，配置持久，最「实验室级」。
- 代价：需要可管理交换机/路由器 + 一次性配置；不是「拎起笔记本就走」。

---

## 4. 方案 C —— 多物理网卡（一子网一口）

**适用**：方案 A 不成立（VLAN 隔离）又没有方案 B 的硬件时的兜底。

Thunderbolt/USB 扩展坞提供多个以太口，一口接一个子网，各配该子网静态 IP。
CAICT 现场当时正是**单网卡、无扩展坞**才卡住——配一个多口坞即可解。受物理口数
限制，子网很多时不如方案 B。

---

## 5. 选型决策树

```
仪表都在同一台交换机、无 VLAN 隔离？
├── 是 → 方案 A（单网卡多 IP 别名）   ← 零硬件，现场便携首选
└── 否（VLAN/多交换机分隔）
        ├── 能加可管理交换机/路由器？ → 方案 B（三层路由）  ← 固定实验室最稳
        └── 不能，但有多口坞？        → 方案 C（多物理网卡）  ← 兜底
```

## 6. 故障排查

- **`✗ ... could not connect: -1073807339`（VI_ERROR_TMO / 超时）对某个仪表，但
  同时另一子网仪表正常** → 八成是**子网不可达**（PC 当前没在那个子网有接口），
  **不是 HAL bug、也不是仪表坏**。先 `nc -vz <ip> <port>` 确认网络层；按方案 A
  把缺的子网 IP 别名加上。
- **网络通（`nc` 成功）但 `*IDN?` 不应答 / SCPI 超时** → 这才是 SCPI 会话层问题
  （仪表忙、single-client 占用、Test App 没起），跟子网无关。
- **F64 是 single-client SOCKET，UXM 多 client 友好**：这点跟子网切换无关，只跟
  SCPI 连接模型有关——别把「F64 被别的客户端占用」误判成子网问题。
- **避免无谓的 N×10s VISA timeout**：在子网未配齐时，对不可达子网的仪表做 HAL
  reload 会逐个 10s 超时。配齐方案 A 后再整体 reload；或一次只 reload 当前可达
  子网的仪表。

## 7. 软件侧支持（MIMO-First, P1-11 增强）

软件改不了路由，但能让「连不上」**看得懂为什么**：

1. **区分「网络不可达」vs「SCPI 不应答」**：readiness 报告把 TCP 层连不上
   （`unreachable`，多半子网不对）与 TCP 通但 `*IDN?` 超时（`scpi_fail`，仪表/
   会话问题）用不同状态标识，不再糊成一个 `fail`。后端 `tcp_preflight`
   （`instrument_hal_service.py`）已具备区分能力，本增强把它接到 readiness 状态。
2. **按子网聚合的可达性视图**：把仪表按 `/24` 子网分组，显示「当前 PC 配置下哪些
   子网可达」，并给可操作提示（如「UXM 所在 `192.168.1.0/24` 不可达：按本指南
   方案 A 加 IP 别名，或确认交换机连线」），surfaced 进 P2-8 主控制台就绪带。

这两点直接把 CAICT 那种「甩一个 `-1073807339` 看不懂」变成「明确告诉你是子网问题
还是仪表问题、该怎么办」。
