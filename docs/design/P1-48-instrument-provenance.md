## 一、这片要解决的那件事

用户 2026-08-09 手工测试时问的原话：

> **「我在 log 里是不是看不出哪些是 mock，哪些是 real 仪表？」**

答案是：**看不出**。而且比「看不出」更糟——**有几处在明确地说反话**。

顺着这条线往下查，挖出来的问题不止日志一处，一共三段：

| 段 | 一句话 | 性质 |
|---|---|---|
| **A** | 日志里的真假标签是错的（不是没有，是反的） | 说谎 |
| **B** | 正式报告不说自己是模拟的，而且「TRP 来源」那栏在说假话 | 一半沉默一半说谎 |
| **C** | 虚拟路测（VRT）用随机数现编 KPI，标着 ✓ PASS 进了正式 PDF | **编的数被当成结论** |

用户的原话问的是 A。但按「这条路径会不会替人下结论」排，**C 最危险**——A/B 是读者自己看不清，C 是系统替读者下了一个假结论。所以本稿的顺序不是完全按用户提问顺序来的，理由写在第五节「顺序与拍板点」。

## 三、跟原始判断不符的发现（诚实清单，不藏）

这些是勘察时跟简报/直觉对不上的地方，直接影响了方案怎么切：

1. **「五个 Mock 类都覆盖了」这句话，计数对、暗示错。** `app/hal/` 下有 **7** 个 Mock 类，`MockVNA` 与 `MockSignalGenerator` 没覆盖。如实收窄：这两个类在我能查到的 8/06–8/09 四个 app.log 里**一次都没被装上过**（mock 轮次是「没选型号」，real 轮次是选了真驱动然后连接超时），是**潜伏**不是正在冒烟；而且它们从不发 SCPI，所以**今天没有绕过正式证据门**。

2. **「连接失败会回退成 mock」这个机制不成立。** 驱动只在 `connect()` 成功时才进 `self.drivers`，失败两条路都只记一行 fail，从不换成 Mock 顶上。唯一的「回落 Mock」发生在**选类阶段**（真驱动根本没注册时）。按原来的说法去排查会找错代码。

3. **手动 SCPI 终端的方向跟直觉相反**（A-8）。HAL 是 mock 时，终端反而打真硬件。若照直觉「跟着 hal_mode 走」去修，会把真机往返标成 mock，**比现状更错**。

4. **A 段真正的缺口比想象的小一档**：`exec-<id>.log` 已经逐行带 `driver_source`（A-10）。所以「执行期日志分不出真假」今天已经不成立，剩下的是 **app.log** 和**非执行期（终端）**两块。

5. **B 段范围比想象的大一档**：用户手点「生成执行报告」的那份**零标注**（B-6）——而那才是他真会点的按钮。

6. **C 段是「从来没做」不是「做了被顶掉」**，而且是**两层假**（C-3/C-5）。只治后端那一层，会把前端编的数**洗成「真实采集」，比现状更隐蔽**。

7. ~~**`docs/roadmap-first-call.md` 里搜不到 `P1-48`**~~ —— **观察属实，归因已澄清**：勘察是在 `main` 上做的，而 P1-48 条目当时在未合并的分支 `docs/p1-48-instrument-provenance`（PR #305）上，`main` 上确实 0 命中。条目本身存在且完整（9 处提及）。⚠ 但这条暴露了一个真实的操作风险：**设计阶段的勘察若跑在 main 上，看不见尚未合并的立项边界**，「越界」就没有外部锚可对。后续切片开工前，先确认 PR #305 已合入 main。

8. **仓里有一道旧门在给谎言背书**（C-7）：`tests/test_feature_gaps.py` 断言 `POST /reports/compare` 返回 200。删端点那片必须把它一起删，否则落地当天全量红在一个没预料的文件上。

9. **判官实测挖出的假门**（这条最要命，见下）：有两套候选方案都用「遍历 `app.routes` 断言那四条 path 不在里面」当删端点的门，并写着「今天必红」。**实测今天就是绿的**——本仓 fastapi 版本下 `include_router` 不展平，子路由根本不在顶层 `app.routes` 里。而这个坑仓里**已经踩过并立了碑**（`tests/test_rule_gates.py` 的 `_expand_app_routes` 就是为此写的）。本稿一律改用 `_expand_app_routes`。

10. **顺带一个跟 P1-48 无关但同目录的事实**：`logs/db.log.2026-08-07` 单文件 1.6 GB。不在本片处理，记进待评估池。

## 四、切片表

主干取「能不改就不改」那条路线：**零新数据库列、零新 API 字段、零新服务/中间件**。真值已经在库里、在类属性上、在日志记录上躺着了，我们只做三件事——**把两个自称真机的 mock 改回实话、把每处「取全局」换成「取这台自己的」、把编数的代码整段删掉**。

一共 **9 片**，每片一个 PR。修法分布：**删掉 4 片 / 换地方取数 4 片 / 收紧 1 片 / 新加一套东西 1 处**（S1 里给虚拟路测的报告构造处新加一个读模拟标记的地方 —— 外审指出那条链上一处都没有，不新加就挡不住）。

### S0 · 把两个自称真机的 mock 改回实话（地基）

| | |
|---|---|
| **不做它什么故障还在** | `MockVNA` / `MockSignalGenerator` 继续自称真机。任何按这两个字段判真假的地方会把它们当真仪表；而 S2/S3/S4 全都要消费这个字段——在一个会说谎的真值源上接消费方，等于把谎固化进更多地方 |
| **改什么** | 给这两个类各补两行 `driver_source = "mock"` / `simulated = True`，跟另外 5 个 Mock 类逐字同形。**共 4 行** |
| **修法** | 收窄（把继承来的过宽默认值收窄到本类真值） |
| **动几个文件** | 2 个源文件（`app/hal/vna.py`、`app/hal/signal_generator.py`）+ 1 个新测试文件 |
| **爆炸半径 X→Y** | X = 这两个模拟驱动被当真机，它们 `np.random` 造的数可被下游判成实测；将来一旦发 SCPI 会直接绕过正式证据门。Y = 判成 mock，结论只会从「假装已验证」变成「未验证」，不新增任何「假装已验证」。**Y ≤ X** |
| **门** | 不变量门，三条断言**全部从生产表派生、不手写清单**：① 遍历 `_MOCK_DRIVER_CLASSES`，断言每个类 `driver_source == "mock"` 且 `simulated is True`；② 遍历真驱动注册表 `_real_driver_registry()` 的每个类，断言 `driver_source == "real"` 且 `simulated is False`；③ 集合等式：`set(_MOCK_DRIVER_CLASSES)` == 「走 `app.hal` 包扫出来的所有名字以 Mock 开头的驱动类」 |
| **让门红的变异** | ㊀ **今天什么都不改直接跑就是红的，红的两个类恰是 `MockVNA` / `MockSignalGenerator`**（红因就是缺陷本身），补完转绿；㊁ 删掉任一 Mock 类的 `simulated = True` → ① 红；㊂ 给任一真驱动加 `simulated = True` → ② 红；㊃ 往 `_MOCK_DRIVER_CLASSES` 加一个新 Mock 类而不声明 ClassVar → ① 红；只声明不进表 → ③ 红 |

**门的实现纪律（必须写进测试注释）**：③ 的类枚举必须按「模块名以 `app.hal` 开头」过滤包扫描出来的成员，**不能用 `__subclasses__()`**——否则会把别的测试文件里临时定义的子类捞进来，造成单文件跑绿、全量跑红的假红（跟 memory 里 alembic 污染那条同形）。

**明确不做的**：不动 `is_mock_driver` 的实现、不统一「类名以 Mock 开头」那几处判据。进待评估池。

⚠️ **原来这里还写着「不把 `_MOCK_DRIVER_CLASSES` 改成由别的表派生」—— 那条已经作废，
S0 实际做的正是这件事**（外审在 #307 抓出这个矛盾）。原因：外审**连续三轮**攻破为
「两张表别走岔」写的那道守门测试（`|=` 增强赋值 / 通过别名改 / 用普通赋值顶替类名，
写法枚举不完）。三轮之后回头看，根子是**同一件事存了两份**，所以把它们合成了一份：
模块级唯一一份 `_MOCK_FALLBACK_BY_CATEGORY`，`_MOCK_DRIVER_CLASSES` 从它派生，
方法内那份局部副本和那道门一起删掉。

**当初判它「越界」判错了** —— 当时的问句是「不改它，两个 mock 类自称真机这个毛病还在吗」，
答「还在」，所以判成不必做。但真正该问的是「**为了守住这件事，我得写一道多复杂的门**」——
写一道靠解析源码猜有没有人动过局部表的门，本身就是信号：**该合并的东西没合并。**

> **为什么不动 `is_mock_driver` 的实现**——这条是本稿否掉某个候选方案最主要的理由：`is_mock_driver` 是 precheck 里**两道正在工作的正式 gate** 的开关（判成 mock 就直接旁路放行）。把它从 isinstance 白名单换成「读属性」，等于把入口域从「7 个已知类」放开成「任何带这个属性的对象」，方向是**放行**。S0 只补属性、不碰判据，这两道 gate 的语义一个字不变。

⚠️ **外审纠正：这三条路不能写死「真」。** 原方案打算给它们固定标上真，
理由是「裸 socket 直连数据库里配的地址，要么真说上话要么报错」。但**那个地址可能指向
仪器模拟器、代理、或者接错的设备** —— 连接照样成功，于是我们把「连上了某个端口」

`unverified`；只有能通过真正的驱动、由权威判断确认来源的那条路，才允许标真或假。
