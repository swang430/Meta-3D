# P1-43 日志历史分页设计

## 四行契约

- 输入：日志文件、每页条数、与 `/system-logs/tail` 相同的过滤条件，以及服务端返回的不透明 `older_cursor`。
- 输出：按时间正序排列的一页更早日志、该页实际扫描行数、下一枚游标与是否仍有更早内容。
- 不变量：`/tail` 继续受 20,000 行扫描上限约束；历史读取只能由显式用户动作触发，不能进入自动轮询路径。
- 失败：游标损坏、跨文件复用或日志被截断/替换时明确拒绝，不把错位内容伪装成连续历史。

## 方案

采用文件内字节位置游标。游标携带版本、文件身份、继续读取的位置、初始快照 EOF，
以及固定 64 字节级别的“分页边界 + 快照 EOF”双锚点，由 GUI 当作不透明字符串原样回传。
服务端从游标位置继续反向扫描，因此翻第 N 页不会重新解析文件末尾；固定大小锚点让每页
游标校验成本为 O(1)，不会随着翻页深度累计重哈希。正常 append 只发生在 snapshot EOF
之后，不会让游标失效；边界或原快照尾部被等长原位改写则返回冲突。输入游标在扫描前后
各校验一次，最终页也不例外。校验、扫描与新游标生成全部绑定同一个已打开文件描述符，
轮转发生在请求中途也不会混读新旧两代文件；下一次请求若路径已换代则按文件身份拒绝。

这里的“冻结快照”只承诺分页边界连续、初始尾部稳定和不混文件代际，不复制或全文哈希
整个日志文件；远离双锚点的既有内容、尚未读取的更早前缀不承诺点时间不可变。这是显式
历史浏览，不是文件系统快照服务。

`GET /system-logs/tail` 仍负责实时尾读，并在原响应上增加 `older_cursor` 与
`has_older`。新增 `GET /system-logs/history` 只接受显式游标，使用独立且有界的单页
扫描预算；即使某页因过滤条件没有匹配项，也必须推进游标，让用户能够继续跨过稀疏
窗口。轮转后的 `*.log.*` 文件纳入文件列表，历史不再只限当天活跃文件。

GUI 将当前尾页和已加载历史作为一个冻结快照展示。首次“加载更早”会关闭自动刷新；
文件或过滤条件变化、手动刷新、重新开启自动刷新都会丢弃历史页并重新建立尾部快照，
避免实时窗口移动后在分页边界产生缺口。关闭刷新同时同步清除 timer，并以 ref 阻断已进入
事件队列的旧回调，保证显式历史请求不会被迟到的 tail 请求覆盖。

mock 环境使用同一份 260 行样本实现 tail/history、过滤、游标校验和稀疏空页推进；历史
功能在无后端开发模式下同样可达，不再固定返回 `has_older=false` 的空壳响应。
