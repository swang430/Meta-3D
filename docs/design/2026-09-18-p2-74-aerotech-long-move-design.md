# P2-74 设计稿：Aerotech 转台「超过 10 秒的移动必然失败」

> 状态：待用户过目，未动代码。Roadmap: P2-74（2026-09-16 现场发现 D8）。

## 1. 可观察故障

2026-09-16 12:13 执行 `7d347c03`：`MOVEABS X -90.0000 XF5.0000`（180°，5°/s，需 36 s）发出后 **恰好 10.0 s**
连接被对端 reset → 非幂等命令结局未知（未重放，正确）→ 重连后 `ABORT X` **过了 8 s 才被确认**（12:13:49.560 发出，
12:13:57.607 才回 `%`）→ 随后 `VFBK(X)` 回了空串，无法证明停止 → 急停。紧接着读到 `PFBK(X) = -0.0017`，16 分钟后下一次连接
读数为 `0`（出发点是 `+90`）：若这期间无人手动转过转台，说明那 8 s 里转台一直在转（18 s × 5°/s ≈ 90°）。

这不是偶发的传输不稳。全部历史 `scpi.log*` 里 33 次 `MOVEABS`：

| 形态 | 次数 | 结局 |
|---|---|---|
| 已在目标位（0 s 返回） | 28 | 全部成功 |
| 10° 小步（2.1 s 返回） | 2 | 全部成功 |
| 需要 > 10 s 的移动（08-27 `X 100`、09-16 `X -90`） | 2 | **都在第 10.0 s 失败**（08-27 是驱动自己的 10 s 超时，09-16 是对端 reset） |
| 命令写错（08-27 `X200.0000` 少空格） | 1 | 空回复 |

**结论：这套驱动在真机上从未成功完成过一次超过约 2 s 的移动。** 下次现场的多方位用例（90° 一步、5°/s = 18 s）会次次失败。

## 2. 根因（有依据的部分）

1. **`MOVEABS` 在该控制器上是阻塞命令**：移动完成才回 `%`。依据：Aerotech 随机样例
   `Samples/AeroBasic/ProgramOffset.ab` 等写明 `WAIT MODE MOVEDONE ' Default mode: Wait for a move to finish`；
   `release.txt` 写明 "The default wait mode is now 'wait for move done'"。驱动自己也知道这一点
   （`_response_timeout_s()` 给 `MOVEABS` / `HOME` / `WAIT INPOS` 用的是 `settle_timeout_s`）。
2. **控制器的 ASCII 套接字有空闲超时**：本地集成说明
   （`Instrument_API_Doc/Aerotech/Aerotech_Ensemble_ASCII_TCP转台控制集成说明.docx`）给出参数
   `Parameters → System → Communication → Ethernet Sockets → Socket2Timeout`，建议「10000 或更高」，
   并注明「避免长时间测量期间连接超时」。实测 reset 恰在 10.0 s，与 10000 ms 吻合。
   阻塞等待期间线路上没有任何往返，控制器把这条连接当成空闲。
3. 两者叠加：**任何行程时间 > 10 s 的移动必然半路断连**。断连后命令结局未知，只能急停。

## 3. 不知道的（不猜，留给现场）

- 控制器上 `Socket2Timeout` 的实际值（只有「10.0 s 被 reset」这一间接证据）。
- 控制器固件版本（U-8：没有安全的型号 / 固件查询）→ 不知道 ASCII 接口是否支持 `WAIT MODE NOWAIT`
  （`release.txt` 的 CTRL-10618 "Added the WAIT MODE command to the ASCII interface" 没法对上版本）。
- 重连后 `ABORT X` 为什么 8 s 才被确认、这 8 s 里转台是否一直在转（位置读数支持「在转」，但不能排除事后人工干预，
  也不能排除那次 `-0.0017` 其实是错位的速度读数）；紧随其后的 `VFBK(X)` 为什么回空串。
  **这是安全相关的疑点**：半路断连时，急停可能有约 8 s 不受控。

## 4. 方案

| | 做法 | 依赖 | 评价 |
|---|---|---|---|
| A | 现场把控制器 `Socket2Timeout` 调大 | 现场、厂商工具、可能要重启控制器 | 治本，但不是代码；没做之前软件照样必败 |
| **B** | **驱动把长移动拆成若干段，每段行程时间低于预算**（只用已在用的 `MOVEABS` + `WAIT INPOS`） | 无 | **推荐**。不引入新命令；每段之间本来就有「确认停稳 + 检查人工急停」，操作员叫停的响应反而更快 |
| C | `WAIT MODE NOWAIT` + 轮询到位 | 须先证实固件支持该命令 | 候选。要先有现场诊断序列的真机回复，不盲试 |
| **D** | **发命令前先估行程时间，超预算且无法分段时直接拒绝** | 无 | **推荐，与 B 配套**。把「半路断连 + 8 s 不受控 + 急停」换成「移动前明确拒绝」 |

推荐 **B + D**，A 写进下次现场清单，C 留候选。

### B + D 的具体形态

- 新增一个连接级配置 `blocking_command_budget_s`（默认 **6 s**，取 10 s 的六成；A 做完后现场可调大）。
  它不是控制器参数的镜像，只是「单条阻塞命令允许占线多久」的软件预算。
- `move_to()`：行程时间 = |目标 − 当前| ÷ feed。不超预算 → 行为与今天完全一样（一条 `MOVEABS`）。
  超预算 → 按 `feed × 预算` 切段（5°/s × 6 s = 30°/段，180° = 6 段），每段走现有的
  「`MOVEABS` → `WAIT INPOS` → `VFBK` / `PFBK` 真值门」，段间检查人工急停。
- 拒绝条件（D）：feed 或当前位置拿不到有限值、单段仍超预算（feed 过低）→ 移动前 fail-loud，给出可操作原因。
- `HOME` 同样是阻塞命令：本片**不改** `HOME`（回零行程不可预估），只在文档与现场清单里注明它同样受 10 s 限制。
- 结局未知的处理、非幂等命令不重放、`ABORT` / 急停逻辑**一律不动**。

### 顺带（同一次排查暴露、同源）

- 单轴台每次连接探测 `PFBK(Y)` 被拒，以 ERROR 级打印（09-16 共 30 次）→ 这是预期内的探测结果，降为 INFO。

## 5. 验收与测试

- 假传输模拟真机行为：任何一条命令阻塞超过 T 秒就 reset 连接。RED：180° 移动在旧代码下失败；GREEN：分段后成功，
  线路上每条 `MOVEABS` 的行程时间都 ≤ 预算，最终 `PFBK` 到位。
- 行程时间 ≤ 预算时线路序列与今天逐条相同（不回归小步移动）。
- 段间人工急停：第 2 段前叫停 → 不再发后续 `MOVEABS`。
- 超预算且无法分段 → 移动前拒绝，线路上零动作命令。
- 每道门配变异实跑。
- 现场载体：`aerotech_positioner_motion_truth` 序列补一步 > 10 s 的移动（B 生效后应成功），并记录 §3 的三个未知。

## 6. 不做

- 不新增、不猜测任何 AeroBasic 命令（C 留候选）。
- 不改 `HOME`、`ABORT`、急停与结局未知的既有逻辑。
- 不改控制器参数（A 属现场动作）。

## 7. 爆炸半径

原故障最坏：移动半路断连 → 约 8 s 不受控转动 → 急停 → 执行失败。
修完最坏：分段逻辑有错 → 某一段被既有的真值门（`VFBK` / `PFBK`）拦下并失败，转台停在段边界；不会出现新的不受控运动。
